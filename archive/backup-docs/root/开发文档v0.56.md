# 类脑活人架构 v0.56
## Engineering Spec / CLI / Always-on / Multi-Agent / Probability-Driven Runtime

> 本版本为 **v0.55 的补全与整合版**。  
> 若 v0.56 与 v0.55 / v0.5 / v0.4 冲突，以 **v0.56** 为准。  
> 本版本不再追求“概念尽可能全”，而追求“可实现、可调参、可降级、可验证、且关键信息不丢层”。

---

## 0. v0.56 修订摘要

v0.56 在 v0.55 的基础上，继续补齐“情境随机性”的工程规格。重点覆盖七类问题：

1. **参数空白** → 补齐默认参数、阈值、上限、场景预设
2. **资源映射抽象** → 给出资源量化、模式阈值、行为偏移映射
3. **冲突闭环不完整** → 引入冲突优先级、最大重采样次数、妥协策略
4. **长期稳定性不足** → 增加存储压缩、缓存上限、过载保护、降级梯度
5. **调试链路不完整** → 明确 trace 存储格式、可视化路径、模块开关与贡献分析
6. **“活人感”不可验证** → 引入场景预设、表达层、量化评估指标
7. **随机性落地不完整** → 引入情境随机层、情绪层面波动、心境波动与强度采样
8. **模块信息遗漏** → 恢复 Agent registry、Skill registry 与 CLI / CIL 详细说明

v0.55 的目标是：

- 让架构 **先能稳定跑起来**
- 让参数 **先能被控制和复现**
- 让异常 **先能被定位和回退**
- 让“拟人感” **先能被测量，而不是只靠主观印象**

## 1. 版本定位

v0.55 不是一份“最终认知科学理论”，而是一份 **可调试的工程规格书**。

### 1.1 核心原则

1. **先离散化，再精细化**  
   先把心理机制压成有限状态、有限参数、有限边界，再逐步拟合真实人类复杂性。

2. **先可跑，再可爱**  
   不允许“活人感”建立在系统不稳、难调、难复现的基础上。

3. **先限权，再开放**  
   任何 Agent 都不能无限放大自身影响；所有偏移必须可裁剪、可降级、可审计。

4. **先场景化，再通用化**  
   对话、陪伴、任务执行是不同 runtime；不再默认同一套权重通吃。

## 3. Agent Registry：补回模块全景、输入输出与职责边界

v0.56 明确恢复 **Agent registry**。  
此前版本虽然保留了公式、阈值与调度逻辑，但模块总表、输入输出边界、唤醒条件、关键技能被压缩得过头，导致实现时容易出现：

- 不知道某个 Agent 何时被唤醒
- 不知道它输出的是 `delta_p`、`sigma_scale` 还是状态更新
- 不知道它失败时该由谁降级接管
- 不知道哪些模块是显性提案者，哪些只是背景偏置器

### 3.1 模块分类原则

| 类别 | 定义 | 是否直接参与最终采样 |
|---|---|---:|
| 显性 Agent | 会主动产出 proposal / veto / mode switch | 是 |
| 隐性 Agent / Module | 只产出偏置、检索结果、时序修正、解释变量 | 间接 |
| Guard / Layer | 不负责“想做什么”，只负责校验、裁剪、授权、渲染 | 是 |
| Control Plane | 调度、预算、持久化、诊断、权限 | 否 |

### 3.6 Agent 唤醒顺序（单轮默认）

```text
state update
-> Salience / Body / Emotion / Relationship / Resource
-> PFC candidate generation
-> Habit / Desire / DMN / Hippocampus / Perspective / Value
-> ConflictMonitor
-> Thalamus sampling
-> BehaviorPlausibilityGuard
-> OutputGate / Renderer
-> writeback / trace / health check
```

### 3.7 必须保留的显隐性边界

1. `PFCAgent` 不能直接越过 `Thalamus` 决定最终动作。  
2. `HippocampusAgent` 不能直接改写关系状态，只能提供记忆证据与 bias。  
3. `OutputGate` 只做门禁与约束，不生成新的高层动机。  
4. `RuntimeController` 是唯一有权实际执行系统动作的层。  
5. `Guard` 模块可以拦截，但不应伪装成普通 Agent 争夺注意力。

## 4. Skill Registry：补回技能层接口、调用协议与降级规则

v0.56 明确恢复 **Skill registry**。  
Agent 不是一团抽象“能力”，而是由可注册、可计时、可降级的 skill 组成。  
实现层应把每个 skill 视为一个 **typed callable**，而不是自然语言描述。

### 4.1 skill 定义

每个 skill 至少包含：

- `name`
- `owner_module`
- `input_schema`
- `output_schema`
- `timeout_ms`
- `cost_class`
- `failure_policy`
- `trace_tags`
- `sync_mode`
- `policy_check`
- `permission_profile`
- `fallback_route`
- `breaker_policy`

推荐统一接口：

```json
{
  "skill": "score_salience",
  "owner_module": "SalienceAgent",
  "input_schema": {
    "event": "RoundEvent",
    "state": "RuntimeState",
    "scenario": "dict[str, Any]",
    "context": "dict[str, Any]"
  },
  "output_schema": "ProposalBundle",
  "timeout_ms": 80,
  "cost_class": "L",
  "failure_policy": "retry_once_then_degrade",
  "trace_tags": ["proposal", "salience"],
  "sync_mode": "sync",
  "policy_check": false,
  "permission_profile": {
    "scope": "compute",
    "external_io": false,
    "social_risk": false
  }
}
```

#### 4.1.1 typed callable contract 约束

实现层应把 `input_schema` / `output_schema` 视为真正的运行时 contract，而不是文档标签。

- contract 可以是 dataclass、primitive、`list[T]`、`dict[K, V]`、`optional[T]`，或封闭对象字段集合。
- registry 初始化时必须 fail fast：非法 type ref、非法 `cost_class` / `failure_policy`、空或重复 `trace_tags`、非法 fallback/breaker 组合都不允许进入运行态。
- `timeout_ms` 必须为正数；`cost_class` 只能是 `L / M / H`；`trace_tags` 必须在运行时被规范化、去重和小写化。
- `RuntimeController` 负责组装 canonical skill inputs；`SkillExecutor` 负责在 provider 调用前后做 typed validation。
- provider 签名必须与声明的 contract 对齐，不应再出现“trace 里的 inputs”和“真实 provider kwargs”不一致的双轨结构。

### 4.4 调用协议

#### 同步 skill
用于单轮路径中不可缺失的计算，例如：

- `score_salience`
- `generate_candidates`
- `aggregate_proposals`
- `sample_action`

运行时要求：

- `RuntimeController` 必须先把输入整理为 contract 对齐的 canonical payload，再调用 `SkillExecutor`。
- `SkillExecutor` 必须先校验输入 contract，再按声明字段调用 provider。
- provider 返回后必须再次按 typed output contract 校验；失败不能被视为“仅仅 shape 不优雅”，而是一次正式 runtime failure。

#### 异步 skill
用于不阻塞主链路的写入、追踪、批处理，例如：

- `flush_trace_batch`
- `checkpoint_create`
- `archive_episode_batch`

异步只改变调度时机，不改变 contract 严格性；异步 skill 同样必须满足 typed input/output validation。

### 4.5 skill 失败策略

| failure policy | 说明 | 适用模块 |
|---|---|---|
| `return_neutral` | 返回中性偏置，不改变分布 | Body / Desire / DMN |
| `fallback_to_prior` | 回退到上一稳定状态或 stable prior，不能退回无意义空壳对象 | Emotion / Relationship / Resource |
| `fallback_to_gist` | 仅返回 gist-only recall 路径，不做细节检索 | Hippocampus |
| `fallback_to_rules` | 切到同 contract 的低成本 heuristic provider route | PFCAgent / Value / Perspective / Renderer |
| `retry_once_then_degrade` | 只重试一次，避免抖动 | Conflict / Salience |
| `trip_circuit_breaker` | 熔断该 skill 一段时间；开路期间 primary 不再尝试，直接由声明的低成本 fallback 接管 | 高成本社交推断 |
| `switch_safe_mode` | 进入系统保守模式 | RuntimeController |

补充语义：

- `fallback_to_rules` 不应再使用静态 shaped payload 伪装成 fallback；必须回到真正的低成本 provider。
- `trip_circuit_breaker` 默认策略为连续 3 次失败开路，冷却 5 轮。
- 任何带 breaker 的 H-skill 都必须声明 lower-cost fallback route。
- `fallback_to_prior` / `fallback_to_gist` 也必须返回与主 skill 相同的 typed output contract。

### 4.6 skill 成本等级

| cost class | 预算说明 | 适合什么 |
|---|---|---|
| `L` | 0~30ms；纯规则 / 数值 | 状态更新、简单打分 |
| `M` | 30~120ms；规则 + 小模型 / 检索 | 估值、关系解释、记忆检索 |
| `H` | 120ms+；主模型或复杂模拟 | 规划、复杂社交视角、最终渲染 |

实现侧必须统一约束：

- 只允许 `L / M / H` 三档。
- `timeout_ms`、`cost_class`、`failure_policy`、`trace_tags` 不得各模块自行解释，必须由 Skill runtime 统一裁决。
- 低成本 fallback 的 `cost_class` 必须严格低于被接管的高成本 primary route。

### 4.7 skill 级 trace 要求

每个 skill 调用至少落盘：

- `round_id`
- `skill_name`
- `owner_module`
- `latency_ms`
- `cost_class`
- `input_hash`
- `output_hash`
- `failure_policy_applied`
- `degraded`
- `seed_ref`（若涉及随机性）
- `fallback_route`
- `fallback_cost_class`
- `policy_rejection_reason`
- `breaker_state`

### 4.8 skill 级权限边界

1. 任何 skill 都不能直接绕过 `RuntimeController` 执行外部动作。  
2. 任何 skill 都不能直接篡改 `proposal_trace` 历史记录。  
3. 涉及社交高风险或外部工具调用的 skill 必须带 `policy_check=true`。  
4. 高成本 skill 被熔断后，只能由低成本 fallback 接管。  
5. skill 不应拿到 controller/store/proposal_trace writer 的可变句柄；状态修改必须通过 typed return payload 表达。  
6. `proposal_trace` 相关 skill 只能 append，不能 rewrite。  

实现层 policy check 至少应消费：

- `mode`
- `safe_mode`
- `operator_level`
- `policy_flags`

## 8. 行为采样总公式（v0.5）

### 5.1 最终行为概率

```text
P_raw(a_i) =
    P_base(a_i)
  + Σ_j [ w_j × Δp_j(a_i) × conf_j ]
  + Δp_context(a_i)

P_final(a_i) = Normalize( Clip(P_raw(a_i), p_floor, p_cap) ) × Gate(a_i)
```

缺省值：

- `p_floor = 0.01`
- `p_cap = 0.85`
- `w_j ∈ [0.2, 1.4]`
- `conf_j ∈ [0, 1]`

### 5.2 置信区间更新

v0.4 的“按场景切换 α/β”过于粗糙。  
v0.5 改为统一更新，再裁剪：

```text
CI_{t+1}(a_i)
= clip(
    CI_t(a_i)
    × narrow_factor(a_i)
    × widen_factor(a_i)
    × overload_guard(a_i),
    CI_min,
    CI_max
  )
```

缺省值：

- `CI_min = 0.08`
- `CI_max = 0.55`

其中：

```text
narrow_factor = 1 - k_if × IF - k_neg × NEG - k_habit × HAB
widen_factor  = 1 + k_idle × IL + k_uncertainty × UNC
overload_guard = 1 + k_overload × OV
```

默认系数：

- `k_if = 0.18`
- `k_neg = 0.22`
- `k_habit = 0.15`
- `k_idle = 0.25`
- `k_uncertainty = 0.10`
- `k_overload = 0.08`

并执行裁剪：

```text
narrow_factor ∈ [0.55, 1.0]
widen_factor ∈ [1.0, 1.45]
overload_guard ∈ [1.0, 1.15]
```

### 5.3 用户给出的 IF / ET / IL 公式的 v0.5 修订版

#### 交互频率 IF

```text
IF = min(1, ( Σ_i exp(-λ·Δt_i) ) / IF_norm )
```

默认：

- `λ = ln(2) / H`
- `H = 3 days`（半衰期）
- `IF_norm = 8`

说明：  
v0.4 用固定窗口 + τ 的表达可行，但工程上更适合用 **半衰期衰减**，便于统一跨 round / 分钟 / 天。

#### 负向体验强度 NEG

```text
NEG = clip(max(0, -S_e), 0, 1)
POS = clip(max(0,  S_e), 0, 1)
```

其中 `S_e ∈ [-1, 1]`。

v0.5 不再直接把体验映射成 `ET ∈ [0.95, 2.0]` 后再乘到 α，原因是：
- 正负项混在一个系数里，调参不直观
- 会放大极端样本
- 不利于线上诊断

改为正负分离，更利于解释。

#### 空闲程度 IL

```text
IL = clip( idle_ratio × (1 - task_load) × (1 - alertness_override), 0, 1 )
```

默认：

- `idle_ratio = min(1, T_idle / T_max_idle)`
- `T_max_idle = 30 min`
- `alertness_override = 1` 当 `salience >= 0.78`，否则 `0`

说明：  
避免“系统明明空闲，但高显著性事件发生时仍错误放宽”的问题。

### 5.4 情境随机层（Contextual Stochasticity Layer）

原则：  
**随机性不直接乘在最终归一化后的概率上**。  
v0.55 采用“确定性倾向 + 情境随机扰动 + 强度采样”的三段式结构：

1. **确定性倾向** 决定大方向
2. **情绪层面波动** 决定本轮更偏哪种情绪表达通道
3. **心境波动** 决定同一情绪通道内的细微差异
4. **强度采样** 决定本轮表现“有多强”

这样可以满足：

- 同一事件不会每次都触发完全相同的动作
- 但输出仍落在合理情绪范围内
- “生气 / 难过”可保持同类倾向，只在程度与细节上波动
- 可复现、可 debug、可裁剪

### 5.5 动作倾向的确定性底座

对每个候选动作 \(a_i\)，先计算未归一化的倾向分数：

```text
u_i(t)
= b_i
+ Σ_agent Δu_agent,i(t)
+ Σ_k w_env,k,i · E_k(t)
+ h_i(t)
```

其中：

- `b_i`：动作基线
- `Δu_agent,i`：各 Agent 对动作 `i` 的贡献，建议直接由 `delta_p` 线性映射到 logit 空间
- `E_k(t)`：环境特征
- `h_i(t)`：惯性 / 滞后项

推荐环境特征最少包含：

- `time_of_day`
- `location_type`
- `privacy_level`
- `noise_level`
- `social_density`
- `novelty`
- `resource_scarcity`
- `circadian_offset`

惯性项采用一阶平滑：

```text
h_i(t)
= λ_h · h_i(t-1)
+ (1 - λ_h) · 1[a_{t-1}=i] · c_i
```

默认：

- `λ_h = 0.72`
- `c_i ∈ [0.02, 0.12]`

解释：  
人类不是每轮都“重新洗牌”；上一轮已经回避、拖延、委屈或强撑，这一轮更容易沿原轨迹延续。

### 5.6 情绪层面波动与心境波动

v0.55 不再使用“家族级波动 / 动作微波动”的命名。  
统一改为：

- **情绪层面波动（emotion-level fluctuation）**
- **心境波动（mood fluctuation）**

#### 5.6.1 情绪层面波动

每个候选动作先映射到一个主情绪通道 `emo(i)`，例如：

- `sadness`
- `anger`
- `fear`
- `withdrawal`
- `comfort_seek`
- `task_hold`

同一情绪通道共享一个随机项：

```text
ξ_emo(g, t) ~ TruncNormal(0, σ_emo^2(t), -2σ_emo, +2σ_emo)
```

其中 `g = emo(i)`。

含义：  
同一轮里，如果系统整体更偏“受伤 / 低落”或更偏“烦躁 / 防御”，这种偏移应同时影响同通道动作，而不是彼此独立乱跳。

#### 5.6.2 心境波动

在同一情绪通道内部，每个动作还拥有一个更小的局部波动：

```text
ξ_mood(i, t) ~ TruncNormal(0, σ_mood^2(t), -σ_mood, +σ_mood)
```

默认：

```text
σ_mood(t) = 0.5 · σ_emo(t)
```

含义：  
同样是难过，这次可能更偏“沉默”，下次可能更偏“解释几句后沉下去”；  
但不会从“难过”直接随机翻成“兴奋”或“攻击”。

### 5.7 随机项的乘性注入方式

定义乘性扰动：

```text
m_i(t) = exp( ρ_emo · ξ_emo(emo(i), t) + ρ_mood · ξ_mood(i, t) )
```

再把它注入未归一化分数：

```text
ũ_i(t) = u_i(t) + log(m_i(t))
```

等价于：

```text
exp(ũ_i) = exp(u_i) · m_i
```

说明：  
这就是“随机乘一个系数”的工程化写法，但**乘在未归一化分数上，而不是最终概率上**。  
这样做的好处是：

- 不会破坏概率分布的数学合法性
- 可以继续自然地做 softmax / normalize
- 更容易对强动作、弱动作和门禁动作做统一裁剪

默认：

- `ρ_emo = 1.00`
- `ρ_mood = 0.60`

### 5.8 情境波动度：决定随机幅度，而不是固定乱抖

随机性幅度不设固定值，而由当前情境波动度 `V_t` 决定：

```text
V_t
= clip(
    0.25 · novelty
  + 0.20 · emotion_volatility
  + 0.15 · fatigue
  + 0.10 · privacy_shift
  + 0.10 · location_shift
  + 0.10 · circadian_offset
  + 0.10 · resource_scarcity
  - 0.10 · salience_lock
  - 0.10 · habit_strength
  , 0, 1
)
```

然后：

```text
σ_emo(t) = σ_emo_min + (σ_emo_max - σ_emo_min) · V_t
σ_mood(t) = σ_mood_min + (σ_mood_max - σ_mood_min) · V_t
```

默认：

- `σ_emo_min = 0.03`
- `σ_emo_max = 0.18`
- `σ_mood_min = 0.015`
- `σ_mood_max = 0.09`

解释：  
越陌生、越疲惫、越波动、越缺资源，随机幅度越大；  
越高显著锁定、越习惯化，随机幅度越小。

### 5.9 基准分布、随机分布与最终混合

先计算无随机基准分布：

```text
P_base_stochastic(a_i) = Softmax(u_i(t))
```

再计算带随机扰动的候选分布：

```text
Q_noise(a_i) = Softmax(ũ_i(t))
```

最终分布采用可调混合：

```text
P_mix(a_i)
= Normalize(
    (1 - λ_noise(t)) · P_base_stochastic(a_i)
  + λ_noise(t) · Q_noise(a_i)
)
```

其中：

```text
λ_noise(t)
= clip(
    λ0
  + 0.25 · V_t
  - 0.12 · control_strength
  + debug_noise_override,
    0,
    λ_runtime_cap
)
```

默认建议：

- `λ0 = 0.10`
- `λ_runtime_cap = 0.60`
- `debug_noise_override = 0`（debug 时可临时放宽）

说明：  
v0.55 **不再设置固定的全局“随机最多只接管 35%”硬约束**。  
随机混合权重改为运行时参数，由场景、控制强度、调试模式共同决定；正式运行建议保守，debug 可放开。

随后再并回主采样流程：

```text
P_final(a_i)
= Normalize( Clip( P_mix(a_i), p_floor, p_cap ) ) × Gate(a_i)
```

### 5.10 强度采样：保证“结果同类，但程度不同”

同一事件下，人类往往不是动作类别变化，而是**表达强度**不同。  
因此 v0.55 要求把“类别采样”和“强度采样”分开。

先估计强度均值：

```text
μ_int(t)
= clip(
    sigmoid(
        γ0
      + γ1 · affect_load
      + γ2 · arousal
      + γ3 · privacy_level
      - γ4 · self_control
      - γ5 · relationship_risk
    ),
    0.05, 0.95
)
```

再定义集中度：

```text
κ_t = clip(16 - 10 · V_t, 4, 16)
```

最终采样：

```text
r_intensity(t) ~ Beta( μ_int(t)·κ_t , (1-μ_int(t))·κ_t )
```

默认：

- `γ0 = -0.20`
- `γ1 = 1.10`
- `γ2 = 0.55`
- `γ3 = 0.35`
- `γ4 = 0.80`
- `γ5 = 0.60`

解释：  
- 高负面负荷、高唤醒、私密场景 → 强度更高
- 高自控、高关系风险 → 强度更低
- 情境越不稳定，强度分布越分散

### 5.11 强度到输出层的映射

采样到的 `r_intensity ∈ [0,1]` 必须写入 OutputStyleLayer，而不是只停在内部状态：

```text
reply_delay
= d_min + r_intensity · (d_max - d_min)

self_disclosure
= s_min + r_intensity · (s_max - s_min)

tone_sharpness
= t_min + r_intensity · (t_max - t_min)

repair_tendency
= r_min + (1 - r_intensity) · (r_max - r_min)
```

含义：

- 同样是受伤，这次可能只是“轻微低落 + 回复慢一点”
- 下次可能是“明显难过 + 更少解释 + 更想独处”
- 但不会跳出合理情绪通道

### 5.13 Query-Intent / Disclosure-Intent 概率层

## 9. ResourceAgent：从抽象隐喻改成量化预算层

### 6.1 统一资源指标

```text
scarcity_index
= clip(
    0.40 * burn_rate_ratio
  + 0.30 * low_balance_ratio
  + 0.20 * queue_pressure
  + 0.10 * latency_pressure,
    0, 1
  )
```

其中：

- `burn_rate_ratio = current_burn / target_burn`
- `low_balance_ratio = 1 - remaining_budget_ratio`
- `queue_pressure = queue_len / queue_cap`
- `latency_pressure = p95_latency / latency_sla`

### 6.2 资源模式阈值

| 模式 | scarcity_index |
|---|---:|
| abundant | [0.00, 0.25) |
| stable | [0.25, 0.50) |
| scarce | [0.50, 0.75) |
| starvation | [0.75, 1.00] |

### 6.3 行为偏移映射

```text
body_hunger_bias       = 0.10 + 0.55 * scarcity_index
effort_avoidance_bias  = 0.05 + 0.45 * scarcity_index
deliberation_compress  = 1.00 - 0.50 * scarcity_index
rumination_bias        = 0.05 + 0.35 * scarcity_index
action_shrink_scale    = 1.00 - 0.40 * scarcity_index
```

### 6.4 映射到具体动作概率

对常见动作类别定义统一偏移：

```text
Δp(delay_reply)      += +0.18 * body_hunger_bias
Δp(short_reply)      += +0.15 * deliberation_compress
Δp(explore_new_path) += -0.20 * action_shrink_scale
Δp(reuse_habit)      += +0.22 * effort_avoidance_bias
Δp(deep_plan)        += -0.25 * effort_avoidance_bias
```

说明：  
这解决了 v0.4 中“饥饿偏置 0.3 究竟意味着什么”的问题。  
在 v0.5 中，任何资源隐喻都必须落到 **动作偏移表** 或 **模块资源占比表** 上。

### 6.5 starvation 模式的硬约束

当 `scarcity_index >= 0.75`：

- 禁止非必要 PerspectiveModel
- 禁止长链 PFC 深规划
- 禁止二次以上重采样
- 输出长度上限降到默认的 40%
- 仅保留：
  - Body/Resource/Thalamus
  - Habit
  - 必要的 Relationship 安全约束
  - 最小 PFC 候选生成

## 11. 冲突闭环：优先级、重采样、妥协规则

### 8.1 冲突分数

```text
conflict_score =
  0.35 * proposal_divergence
+ 0.20 * veto_tension
+ 0.20 * value_gap
+ 0.15 * relation_risk_gap
+ 0.10 * body_state_gap
```

### 8.2 冲突优先级

出现冲突时，按以下顺序裁决：

1. **生理 / 安全约束**
2. **系统预算 / 过载约束**
3. **关系安全 / 边界约束**
4. **任务目标**
5. **即时欲望**
6. **好奇 / 探索 / DMN 漫游**

### 8.3 重采样规则

- `conflict_score < 0.65`：不重采样
- `0.65 <= conflict_score < 0.82`：允许 1 次重采样
- `>= 0.82`：最多 2 次重采样，且必须启用妥协模板

### 8.4 多轮冲突后的妥协模板

若达到 `max_resample_rounds` 仍冲突，禁止继续死循环，强制落到以下模板之一：

1. **生理优先妥协**：缩短输出、延迟动作、减少承诺
2. **关系优先妥协**：保留礼貌边界，降低自我暴露
3. **任务优先妥协**：给最小可执行下一步，不做展开
4. **预算优先妥协**：走习惯路径或模板路径

### 8.5 冲突死锁熔断

若连续 `3` 轮进入 `critical conflict`：

- 输出 `hesitation / uncertainty` 风格
- 禁止 high-risk action
- 强制提升 PFC + Conflict 权重 1 轮
- 给 Runtime 打 `conflict_hot` 标记，持续 5 轮

## 12. HabitAgent：补足量化、上限与恢复规则

### 9.1 习惯强度公式

```text
habit_strength_t =
clip(
    (1 - decay_h) * habit_strength_{t-1}
  + η_pos * positive_feedback
  - η_neg * negative_feedback
  + η_rep * repeat_signal
  + η_ctx * context_similarity,
    0, 1
)
```

默认：

- `decay_h = 0.015 / tick`
- `η_pos = 0.06`
- `η_neg = 0.08`
- `η_rep = 0.04`
- `η_ctx = 0.03`

### 9.2 反馈时效系数

```text
feedback_weight(Δr) = exp(-ln(2) * Δr / H_fb)
```

默认：

- `H_fb = 6 rounds`

所以：

- 即时反馈 ≈ 1.0
- 6 轮后 ≈ 0.5
- 10 轮后 ≈ 0.32

### 9.3 默认动作建议阈值

| habit_strength | 含义 |
|---|---|
| < 0.35 | 不足以接管 |
| 0.35~0.60 | 只提供候选偏移 |
| 0.60~0.80 | 低冲突场景可默认接管 |
| > 0.80 | 高稳定默认路径，但仍受 Guard 裁剪 |

### 9.4 反向习惯突破奖励上限

v0.4 的“额外提升 Δp”没有上限。  
v0.5 改为：

```text
breakthrough_bonus = min(0.08, 0.04 + 0.06 * success_signal)
```

并且：

- 同一上下文 10 轮内最多触发 2 次
- 不允许单次将新行为概率抬升超过 `+0.10`
- 旧习惯不会瞬间清零，而是进入 `suppressed but recoverable` 状态

### 9.5 旧习惯受干扰后的恢复

若旧习惯被新行为压制：

```text
recovery_rate = 0.02 + 0.03 * context_recurrence
```

说明：  
这保证“人类习惯改变是渐进的”，而不是一次正反馈就彻底改头换面。

## 16. 故障兜底：从“崩了就替换 baseline”改成降级梯度

### 13.1 Agent 响应梯度

| 状态 | 判定 | 处理 |
|---|---|---|
| healthy | 正常响应 | 正常参与 |
| slow | 超时但有响应 | 降权到 0.6，保留上轮输出平滑 |
| degraded | 连续 2 轮超时 / 异常 | 降权到 0.3，仅允许 neutral delta |
| failed | 连续 3 轮失败 | baseline 代替，并记录故障 |
| quarantined | 高频异常 | 暂停 20 轮，仅健康检查 |

### 13.2 Light Cache Mode 细化

当记忆层读写失败时，切到轻量缓存模式：

- `session_cache_cap = 256 items`
- `ttl = 2 hours`
- FIFO + LRU 混合淘汰
- 只缓存：
  - 最近互动摘要
  - 关系关键 delta
  - 当前 habit 命中
  - 未落盘 trace 索引

### 13.3 概率异常保护

出现以下任意情况即触发回退：

- NaN / inf
- 归一化后概率和偏离 `1 ± 0.01`
- 超过 `3` 个动作同时到 `p_cap`
- `sigma_scale <= 0`

处理顺序：

1. clip
2. rollback 上一轮有效参数
3. 退回 baseline 分布
4. 若连续 3 轮仍异常，进入 `safe mode`

### 13.4 Safe Mode

safe mode 下仅保留：

- Body / Resource
- Relationship 安全边界
- 最小 PFC
- Thalamus
- OutputGate

并禁止：

- DMN
- Perspective
- 二次重采样
- 长回复

## 17. 长期运行：防膨胀、防抖动、防过载

### 14.1 存储膨胀控制

| 层 | 热存上限 | 处理方式 |
|---|---:|---|
| WorkingMemory | 3 propositions | 覆盖写 |
| Episodic hot | 500 | 超出即压缩 |
| HabitMemory | 200 active patterns | 低频链路降级为 dormant |
| RelationshipMemory | 128 entities | 长尾对象冷冻 |
| SchemaMemory | 256 chunks | 合并重复 schema |
| RawEvidenceStore | 2GB 或 30 天 | 过期归档/哈希化 |

### 14.2 Habit 高频缓存

对最近 20 个高频 context 开启命中缓存：

- TTL = 30 min
- 命中后直接跳过完整检索
- 但遇到：
  - 高显著性
  - 高冲突
  - 关系变动
  - 安全标记
  时强制失效

### 14.3 过载保护

引入事件保险丝：

```text
event_fuse_triggered if
  input_rate > rate_cap
  or queue_len > queue_cap
  or cpu_pressure > 0.90
```

缺省：

- `rate_cap = 12 events / 10 sec`
- `queue_cap = 64`
- `cpu_pressure = host specific normalized metric`

触发后：

- 丢弃低优先级 idle 事件
- 冻结 DMN
- 简化输出
- 合并重复输入
- 对恶意 prompt / 高频 CLI 做节流

## 19. 隐性模块调试：开关、权重、贡献度

### 16.1 模块开关

所有隐性模块必须支持：

- enable / disable
- hard weight override
- ablation test
- dry-run mode

### 16.2 贡献度量化

对隐性模块采用 **ablation delta** 近似贡献：

```text
contribution(module, action)
= P_with(module, action) - P_without(module, action)
```

每 20 轮抽样做一次，不要求每轮都算，避免成本爆炸。

### 16.3 建议输出

| 模块 | 贡献指标 |
|---|---|
| CerebellarPredictor | latency smoothing, interruption recovery gain |
| PerspectiveModel | misunderstanding risk reduction |
| Hippocampus | recall hit gain, repetition compression gain |
| Unconscious | baseline bias drift |

## 21. 输出表达层：补上“概率类人 ≠ 表达类人”的断层

### 18.1 新增 OutputStyleLayer

该层不决定“做什么”，只决定“怎么表现出来”，并接收情境随机层输出的 `r_intensity`、`ξ_emo`、`ξ_mood` 作为表达扰动输入。

输出维度：

- `latency_style`
- `sentence_fragmentation`
- `hedging_level`
- `warmth_level`
- `directness_level`
- `repair_tendency`

### 18.2 典型映射

#### 疲惫
- 平均延迟增加 10%~25%
- 句子更短
- 少用复杂从句
- 更倾向先给结论再补充

#### 走神
- 局部插入修正词
- 句法略松
- 更容易出现“停一下再回来”的表达

#### 高边界
- 减少自我暴露
- 提高礼貌但降低亲昵
- 提高拒绝时的简洁度

#### 高依恋但高 tension
- 更可能“绕弯确认”
- 先试探、再靠近
- 减少过直白表达

### 18.3 节奏随机性边界

为避免“机械固定节奏”，引入微扰，但必须受限：

```text
timing_jitter ∈ [-0.08, +0.12]
fragmentation_jitter ∈ [-0.05, +0.10]
```

## 23. 评估体系：把“活人感”拆成能打分的指标

### 20.1 评估维度

| 维度 | 指标 | 目标 |
|---|---|---|
| 稳定性 | 崩溃率 / safe mode 触发率 | 越低越好 |
| 冲突闭环 | resample 死循环率 | < 0.5% |
| 资源适配 | scarcity 模式切换后的 burn 降幅 | scarce 后 3 轮内下降 ≥ 20% |
| 习惯渐进性 | 新习惯达到 0.7 强度所需中位轮数 | 8~30 轮 |
| 记忆拟人性 | gist recall/detail recall 比 | 先 gist 后 detail |
| 表达拟人性 | 节奏方差 / 句长方差 / 修正率 | 不为零但受控 |
| 关系一致性 | 关系状态与表达风格匹配率 | > 85% |
| 任务可靠性 | task 模式下执行成功率 | > 90% |
| 可解释性 | why-this 能还原主要驱动 | Top-3 驱动覆盖率 > 80% |

### 20.2 关键“活人感”指标定义

#### 习惯渐进性
```text
habit_gradient = Δ habit_strength / round
```
目标：
- 平稳上升，避免单轮暴涨 > 0.15

#### 情绪真实性
- 情绪不应每轮剧烈翻转
- 相邻 3 轮情绪方向翻转率应低于 35%
- 但不能低到“毫无波动”

#### 记忆真实性
- detail recall 命中率应低于 gist recall
- 高线索下 detail recall 可恢复
- 低线索下禁止伪造细节

### 20.3 验证方法

1. **离线模拟**：回放标准化事件流
2. **A/B ablation**：关闭单模块观察退化
3. **人工审查**：对 why-trace 与最终输出一致性打分
4. **长跑测试**：至少 10k rounds 稳定性测试

## 27. 对 v0.4 / v0.5 的最终修正结论

v0.4 的价值在于：**理论框架完整**。  
v0.5 的价值在于：**第一次把这套框架压成可执行规格**。  
v0.55 的价值在于：**把“像人但不失控”的随机性正式工程化**。

本版本明确承认三件事：

1. **不是所有心理机制都适合一开始就做成模型**
2. **不是所有“活人感”都来自更复杂的推理**
3. **没有参数边界、日志、降级和评估，所谓“类人”一定会失控**

## 28. v0.56 的一句话概括

> v0.55 不是继续堆概念，而是把“类脑活人 runtime”收敛成一套带默认参数、场景预设、资源约束、冲突闭环、故障降级、情境随机层、可视化调试与量化评估的工程规格书：先把它稳定地造出来，再逐步把它养得更像人。

---

## 29. 必须保留的三条类人记忆原则

1. **记不住全部，只能记住结构**
2. **概括会反过来影响细节回忆**
3. **会暂时忘记，但在足够好的线索下能想起来**

这些原则在 v0.5 中对应：

- gist/detail 双阈值召回
- reconsolidation 对 recall 的反向塑形
- cue-triggered recovery
- interference 只削弱可及性，不等于永久删除

---

## 30. v0.56 仍未完全解决的问题

以下问题在本版被约束，但尚未彻底解决：

1. **主模型输出的人类细节感** 仍取决于 renderer 质量
2. **Relationship / Perspective 的长期一致性** 仍需要真实长跑数据调参
3. **多用户 / 多会话共享资源** 的调度策略尚未展开
4. **“像人但不越界”** 的安全边界仍需要更细的 policy 层
5. **情境随机层在不同文化 / 场景中的校准** 仍需要真实长跑数据与人工审查共同修正

因此，v0.55 可视为：
- **能启动工程实现的版本**
- 但不是最终的生产稳定版
